\section{Euler warm-up [10 points]}
\textbf{Question 1: What is the module system, and how is it used?}\\
The module system (Lmod, a Lua-based environment modules implementation) is used on HPC systems to dynamically manage software environments. It allows users to load, unload, and switch between different software versions without manually modifying system paths.\\
Loading all software globally would lead to conflicts between different versions of compilers and libraries. The module system avoids this problem by dynamically modifying environment variables.\\
In practice, before compiling or running programs on Euler, users load the required modules (e.g., compilers or libraries) inside their batch scripts using commands such as \texttt{module load}.\\

\textbf{Question 2: What is Slurm, and what is its purpose?} \\
Slurm is an open-source workload manager and job scheduler for Linux and Unix-like systems, widely used by supercomputers and clusters. It schedules and executes jobs on compute nodes, handling resource allocation, queuing, and execution control.\\
In particular (from the Slurm documentation), it provides three main functions:
\begin{itemize}
  \item it allocates exclusive and/or non-exclusive access to resources (compute nodes, CPUs, memory, GPUs) to users for a specified duration of time so they can perform work;
  \item it provides a framework for starting, executing, and monitoring work (normally a parallel job) on the set of allocated nodes.
  \item it arbitrates contention for resources by managing a queue of pending jobs.
\end{itemize}

Proceeding as in the example given in the project description, the hardware specifications can be obtained from the Euler webpage. \\

 For Euler VII (phase 2), the system consists of $n_{\text{nodes}} = 248$ nodes, each with $n_{\text{sockets}} = 2$ sockets and $n_{\text{cores}} = 64$ cores per socket, operating at a frequency $f = 2.45\,\text{GHz}$.\\

Using the uops.info database provided, we determine both the superscalability factor and the FMA factor for the corresponding AMD architectures. \\
For both Euler VII phases, which are based on AMD Zen2 and AMD Zen3 respectively, we obtain $n_{\text{super}} = 2$ and $n_{\text{FMA}} = 2$.\\

The FMA factor is determined by observing that all instructions marked as FMA in the table have a corresponding number of micro-operations equal to one. This indicates that the fused multiply-add is executed as a single micro-operation by dedicated hardware. Since an FMA instruction performs the operation $a \cdot b + c$, it consists of one floating-point multiplication and one floating-point addition. Therefore, each FMA instruction corresponds to two floating-point operations, and thus $n_{\text{FMA}} = 2$.

The superscalability is defined as the number of floating-point operations that the FPU of a core can execute in parallel within a single clock cycle. To determine this value, we analyze the instruction \texttt{VFMADD132PD (YMM, YMM, YMM)} reported in the uops.info table. The table specifies the throughput $0.50$ cycles/instruction implies 2 vector FMA instructions can be issued per cycle. Since the table indicates execution on FP0/1, we conclude the core can sustain two FMA pipelines, hence $n_{\text{super}} = 2$. The factor $n_{\text{FMA}}=2$ then accounts for mul+add inside FMA a throughput of $0.50$ cycles per instruction, one micro-operation, and execution on ports FP0/1.

Hence, for both AMD Zen~2 and AMD Zen~3, the superscalability is
2 \text{ floating-point operations per cycle per core}.\\

To determine $n_{\text{SIMD}}$, we inspect the floating-point instructions reported in the uops.info table, where instructions such as \texttt{VFMADD132PD (YMM, YMM, YMM)} appear. The presence of YMM operands indicates the use of 256-bit AVX registers, since YMM registers are defined as 256-bit wide in the AVX/AVX2 instruction set. As both AMD Zen~2 and Zen~3 execute these YMM-based instructions, they necessarily support AVX2 with 256-bit SIMD registers. A double-precision floating-point number occupies 64 bits; therefore, the number of doubles that can be processed concurrently by one SIMD instruction is

$$
n_{\text{SIMD}} = \frac{256}{64} = 4.
$$

Hence, each SIMD instruction can operate on four double-precision values in parallel.

\subsection{Performance model: A simple roofline model [16 Points]}
A (naive) roofline model provides an upper bound on the attainable performance of a kernel as a function of
its operational intensity $I$ (in Flops/Byte). For a given hardware, the attainable performance is bounded by:
\begin{itemize}
  \item a \textbf{compute ceiling} given by the peak floating-point performance $P_{\text{peak}}$ (in GFlops/s),
  \item a \textbf{bandwidth ceiling} given by $B \cdot I$, where $B$ is the sustainable memory bandwidth (in GBytes/s).
\end{itemize}
Hence the roofline bound is
$$
P(I) = \min\left(P_{\text{peak}},\; B \cdot I\right).
$$

The transition between memory-bound and compute-bound regimes occurs at the \textbf{ridge point}:
\begin{equation}
I_{\text{ridge}} = \frac{P_{\text{peak}}}{B}.
\label{eq:ridge}
\end{equation}
A kernel with $I < I_{\text{ridge}}$ is memory-bound, while a kernel with $I > I_{\text{ridge}}$ is compute-bound.\\

From the previous exercises, we have already computed the peak performance $P_{\text{peak}}$ and the sustainable memory bandwidth $B$ for both Euler VII phases. The values of the single core peak performances where
\begin{align*}
P_{\text{peak,1}} &= 41.6~\text{GFlops/s} \quad \text{(Euler VII phase 1, AMD EPYC 7H12 @ 2.6 GHz)},\\
P_{\text{peak,2}} &= 39.2~\text{GFlops/s} \quad \text{(Euler VII phase 2, AMD EPYC 7763 @ 2.45 GHz)}.
\end{align*}
\\
We use the STREAM \texttt{Triad} bandwidth as sustainable memory bandwidth, since it represents a
typical streaming workload (three arrays, two loads + one store per iteration) and is commonly used in
roofline constructions.
From our STREAM outputs, we have the following sustainable memory bandwidths:
\begin{align*}
B_{1} &= 19668.1~\text{MB/s} = 19.6681~\text{GB/s},\\
B_{2} &= 149198.6~\text{MB/s} = 14.2~\text{GB/s},
\end{align*}
where we convert MB/s to GB/s by dividing by $1000$.\\
Using Eq.\ref{eq:ridge}:
\begin{align*}
I_{\text{ridge,1}} &= \frac{P_{\text{peak,1}}}{B_1}
= \frac{41.6}{19.6681}
\approx 2.12~\text{Flops/Byte},\\
I_{\text{ridge,2}} &= \frac{P_{\text{peak,2}}}{B_2}
= \frac{39.2}{14.2}
\approx 2.76~\text{Flops/Byte}.
\end{align*}

\section{Auto-vectorization [10 points]}

\textbf{Question 1: what is data alignment and is it important for data structures to be aligned?}\\
Data alignment refers to placing an object in memory at an address that is a multiple of some power-of-two boundary (for example, 16 bytes). In the document, alignment is discussed as a key performance property for SIMD loads/stores: Intel SSE (and similarly other SIMD ISAs) prefers aligned memory references, and data movement instructions can be significantly more efficient when the data is aligned. The text also warns that using aligned data-movement instructions with incorrectly aligned addresses can even raise an exception (so alignment assertions must be correct).\\
Because of this, it is generally important that frequently accessed arrays/structures used in vectorized loops are aligned (e.g., 16-byte boundaries for SSE), especially when you want the compiler to generate efficient aligned vector loads/stores and avoid extra fix-up code.\\

\textbf{Question 2: what are some obstacles that can prevent automatic vectorization by the compiler?}\\
The PDF emphasizes that some patterns do not always make vectorization impossible, but they often make it unattractive or unsafe, so the compiler may refuse to vectorize. Typical obstacles include: :
\begin{enumerate}
  \item \textbf{Non-contiguous memory access}: loops with non-unit stride or indirect addressing (e.g.\ indexing through another array) usually require multiple loads instead of a single packed load, so the compiler often decides vectorization is inefficient. 
  \item \textbf{Data dependencies across iterations}: SIMD changes the effective order of operations across iterations; if the compiler cannot prove independence, it may report vector dependence and avoid vectorization.
  \item \textbf{Non-vector-friendly loop form}: to be vectorizable, loops should be countable (trip count known at entry and not data-dependent), have a single entry/exit, and contain straight-line code without unsupported control flow such as \texttt{switch}. 
  \item \textbf{Function calls inside the loop}: even a print statement can block vectorization; main exceptions are intrinsic math calls or calls that can be inlined.
  \item \textbf{Pointer aliasing and complex pointer usage}: if the compiler cannot prove that two memory references are distinct (aliased pointers), it must assume possible dependencies and may not vectorize.
\end{enumerate}

\textbf{Question 3: is there a way to help the compiler to vectorize and how?}\\
Yes, the guide explicitly states that users can help by supplying additional information (through hints / pragmas / keywords) and by writing code in a vector-friendly style.
Concrete ways mentioned include:
\begin{enumerate}
  \item \textbf{Provide dependence/alignment hints with pragmas}: \texttt{\#pragma ivdep} asks the compiler to ignore assumed vector dependencies; \texttt{\#pragma vector \{aligned|unaligned|always|...\}} can specify how to vectorize and can override efficiency heuristics.
  \item \textbf{Use \texttt{restrict} to reduce aliasing}: in C99, \texttt{restrict} can assert that pointers do not alias; this can enable vectorization and avoid conservative runtime checks.
  \item \textbf{Communicate alignment properties}: you can align objects with declarations such as \texttt{\_\_declspec(align(...))} and you can also tell the compiler to assume an alignment via \texttt{\_\_builtin\_assume\_aligned(a,n)} or more generally \texttt{\_\_builtin\_assume(cond)}. 
  \item \textbf{Adopt vector-friendly data layouts}: the document highlights that SoA (structure of arrays) tends to give unit-stride streams that are more amenable to effective vectorization than AoS (array of structures).
\end{enumerate}

\textbf{Question 4: which loop optimizations are performed by the compiler to vectorize and pipeline loops?}
The text connects better vectorization to enabling \emph{high-level optimizations} (HLO, typically \texttt{O3}), which ``enables additional loop optimizations'' that make vectorization easier after transformations.\\
It also describes transformations that either create a vectorizable innermost loop or improve alignment and memory behavior, notably: 
\begin{enumerate}
  \item \textbf{Loop unrolling}: auto-vectorization is described as generating packed SIMD instructions to unroll a loop, and the PDF notes that unrolling is something the compiler does automatically (so manual unrolling is typically discouraged when done only to ``force'' vectorization). 
  \item \textbf{Loop peeling for alignment}: the document explicitly mentions code restructuring such as loop peeling to obtain aligned memory accesses throughout the program (e.g., to reach 16-byte alignment for SSE).
  \item \textbf{Loop interchange / collapsing / materialization effects}: vectorization normally targets the innermost loop; however, the PDF notes that prior optimizations such as unrolling, collapsing, or interchange can transform an original outer loop into an innermost loop that becomes the vectorization target.
\end{enumerate}
In short, the compiler typically applies loop transformations (especially under higher optimization levels) to produce a regular, countable, straight-line innermost loop, and may add alignment-related transformations (like peeling) so the vector loop can run efficiently. \\

\textbf{Question 5: what can be done if automatic vectorization by the compiler fails or is sub-optimal?}
The PDF suggests a progression from diagnosis, to restructuring, to stronger user guidance, and finally to more explicit SIMD approaches. 
A practical sequence is:
\begin{enumerate}
  \item \textbf{Inspect vectorization reports and diagnostics}: use compiler optimization reports (e.g.\ \texttt{-qopt-report} in the examples) to see why a loop was not vectorized or why it was considered inefficient. 
  \item \textbf{Rewrite the loop in a vectorizable style}: simplify termination conditions, ensure the loop is countable, avoid unsupported control flow and most function calls, avoid loop-carried dependencies, and prefer unit-stride array accesses over complex pointer arithmetic. 
  \item \textbf{Add correct hints/annotations}: apply \texttt{restrict} to eliminate aliasing ambiguity, assert/assume alignment where valid, and use pragmas like \texttt{\#pragma ivdep} or \texttt{\#pragma vector always} to override conservative assumptions or heuristics (with the caution that incorrect use can change program semantics or even crash with misaligned aligned-load instructions). 
  \item \textbf{Use user-mandated SIMD}: \texttt{\#pragma omp simd} enforces vectorization semantics; unlike mere ``hints'', it makes the compiler warn if it cannot vectorize and provides clauses to specify the required SIMD behavior.
  \item \textbf{Enable more global optimization context}: enabling IPO (interprocedural optimization) and HLO can provide extra information (trip counts, alignment, dependencies) and enable transformations (and inlining) that improve vectorization opportunities. 
  \item \textbf{Move to more explicit SIMD programming when needed}: if automatic vectorization remains insufficient, the document points to approaches where vectorization is expressed more explicitly (e.g.\ explicit SIMD extensions), giving you tighter control and reducing reliance on compiler heuristics.
\end{enumerate}

\section{Matrix multiplication optimization [30 points]}
\textbf{Task 1: Improve the loop ordering in \path{dgemm_jki.c}.}\\
The original naive implementation uses the loop order $i$--$j$--$k$:
\begin{lstlisting}[style=grayverbatim,language=C]
void square_dgemm(int n, double* A, double* B, double* C) {
  for (int i = 0; i < n; ++i) {
    for (int j = 0; j < n; ++j) {
      for(int k = 0; k < n; ++k) {
        C[i+j*n] += A[i+k*n] * B[k+j*n];
      }
    }
  }
}
\end{lstlisting}
Although correct, this ordering is not cache-friendly for column-major storage (indexing $i + jn$). In particular, in the innermost loop over $k$ the access to $A[i+k n]$ jumps across different columns of $A$ with stride $n$, limiting spatial locality.

To improve data locality, we reorder the loops to $j$--$k$--$i$ and hoist invariant quantities out of the innermost loop:
\begin{lstlisting}[style=grayverbatim,language=C]
void square_dgemm(int n, double* A, double* B, double* C) {
  for (int j = 0; j < n; ++j) {
    double* Ccol = C + j*n;              // C(:,j)
    for (int k = 0; k < n; ++k) {
      const double bkj = B[k + j*n];     // B(k,j) reused for all i
      const double* Acol = A + k*n;      // A(:,k)
      for (int i = 0; i < n; ++i) {
        Ccol[i] += Acol[i] * bkj;        // stride-one on C and A
      }
    }
  }
}
\end{lstlisting}

With column-major layout, full columns are contiguous in memory. Therefore, for fixed $(j,k)$ the innermost loop over $i$ accesses both $A(:,k)$ and $C(:,j)$ with \emph{stride 1} (contiguous memory), improving cache utilization and hardware prefetching, and enabling better SIMD vectorization. Additionally, loading $B(k,j)$ once into a scalar (\texttt{bkj}) and using column pointers (\texttt{Acol}, \texttt{Ccol}) reduces repeated address computations and memory loads. The computation remains mathematically identical, since it still accumulates
\[
C_{i,j} \mathrel{+}= \sum_{k=0}^{n-1} A_{i,k} B_{k,j},
\]
but with a more efficient memory-access pattern.\\

\textbf{Task 2: Implement blocking for square matrix multiplication in \url{dgemm_blocked.c}}\\
To further increase performance, we implement \emph{blocking} for the matrix multiplication. Instead of multiplying the full matrices at once, we split the iteration space into smaller $BS\times BS$ tiles and compute partial products tile-by-tile:
\begin{lstlisting}[style=grayverbatim,language=C]
void square_dgemm(int n, double* A, double* B, double* C)
{
  for (int jj = 0; jj < n; jj += BS) {
    int jmax = imin(jj + BS, n);

    for (int kk = 0; kk < n; kk += BS) {
      int kmax = imin(kk + BS, n);

      for (int ii = 0; ii < n; ii += BS) {
        int imax = imin(ii + BS, n);

        for (int j = jj; j < jmax; ++j) {
          for (int k = kk; k < kmax; ++k) {
            double bkj = B[k + j * n];
            for (int i = ii; i < imax; ++i) {
              C[i + j * n] += A[i + k * n] * bkj;
            }
          }
        }
      }
    }
  }
}
\end{lstlisting}

The outer loops \texttt{jj}, \texttt{kk}, and \texttt{ii} iterate over tiles of columns/rows with step size \texttt{BS}. For each block triple, the inner loops perform the same $j$--$k$--$i$ update as in the reordered implementation, but restricted to the current subranges:
\[
j \in [jj, j_{\max}),\quad k \in [kk, k_{\max}),\quad i \in [ii, i_{\max}).
\]
The helper \texttt{imin} ensures correct handling of boundary tiles when $n$ is not a multiple of $BS$.\\
Blocking improves cache efficiency because, for a fixed $(jj,kk,ii)$ triple, the algorithm repeatedly reuses the same tiles of $A$ and $B$ while updating the corresponding tile of $C$. This increases \emph{temporal locality} and reduces the number of times data is fetched from main memory. Inside each tile, the innermost loop still runs over $i$, giving stride-1 (contiguous) access for $A(:,k)$ and $C(:,j)$ in column-major format. Finally, loading \texttt{bkj = B(k,j)} once per $(j,k)$ pair (scalar reuse) avoids redundant memory loads within the innermost loop.\\

We set the default block size to $BS=64$, which is a commonly used baseline for tiled DGEMM.
With double-precision elements, a $64\times 64$ tile corresponds to $64^2\cdot 8 \approx 32$\,KiB per matrix tile; the combined working set of the three tiles $(A,B,C)$ is about $3\cdot 32 \approx 96$\,KiB, which is small enough to benefit from cache reuse while being large enough to amortize loop overhead. 
Moreover, using a power-of-two block size simplifies addressing and often interacts well with cache-line behavior. 
The block size is kept configurable via \texttt{\#ifndef BS} so that alternative values (e.g.\ 32 or 48) can be explored if further tuning is desired.
