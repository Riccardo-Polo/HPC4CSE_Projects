\textbf{Question 1: What is the module system, and how is it used?}\\
The module system (Lmod, a Lua-based environment modules implementation) is used on HPC systems to dynamically manage software environments. It allows users to load, unload, and switch between different software versions without manually modifying system paths.\\
Loading all software globally would lead to conflicts between different versions of compilers and libraries. The module system avoids this problem by dynamically modifying environment variables.\\
In practice, before compiling or running programs on Euler, users load the required modules (e.g., compilers or libraries) inside their batch scripts using commands such as \texttt{module load}.\\

\textbf{Question 2: What is Slurm, and what is its purpose?} \\
Slurm is an open-source workload manager and job scheduler for Linux and Unix-like systems, widely used by supercomputers and clusters. It schedules and executes jobs on compute nodes, handling resource allocation, queuing, and execution control.\\
In particular (from the Slurm documentation), it provides three main functions:
\begin{itemize}
  \item it allocates exclusive and/or non-exclusive access to resources (compute nodes, CPUs, memory, GPUs) to users for a specified duration of time so they can perform work;
  \item it provides a framework for starting, executing, and monitoring work (normally a parallel job) on the set of allocated nodes.
  \item it arbitrates contention for resources by managing a queue of pending jobs.
\end{itemize}

Proceeding as in the example given in the project description, the hardware specifications can be obtained from the Euler webpage. \\

 For Euler VII (phase 2), the system consists of $n_{\text{nodes}} = 248$ nodes, each with $n_{\text{sockets}} = 2$ sockets and $n_{\text{cores}} = 64$ cores per socket, operating at a frequency $f = 2.45\,\text{GHz}$.\\

Using the uops.info database provided, we determine both the superscalability factor and the FMA factor for the corresponding AMD architectures. \\
For both Euler VII phases, which are based on AMD Zen2 and AMD Zen3 respectively, we obtain $n_{\text{super}} = 2$ and $n_{\text{FMA}} = 2$.\\

The FMA factor is determined by observing that all instructions marked as FMA in the table have a corresponding number of micro-operations equal to one. This indicates that the fused multiply-add is executed as a single micro-operation by dedicated hardware. Since an FMA instruction performs the operation $a \cdot b + c$, it consists of one floating-point multiplication and one floating-point addition. Therefore, each FMA instruction corresponds to two floating-point operations, and thus $n_{\text{FMA}} = 2$.

The superscalability is defined as the number of floating-point operations that the FPU of a core can execute in parallel within a single clock cycle. To determine this value, we analyze the instruction \texttt{VFMADD132PD (YMM, YMM, YMM)} reported in the uops.info table. The table specifies the throughput $0.50$ cycles/instruction implies 2 vector FMA instructions can be issued per cycle. Since the table indicates execution on FP0/1, we conclude the core can sustain two FMA pipelines, hence $n_{\text{super}} = 2$. The factor $n_{\text{FMA}}=2$ then accounts for mul+add inside FMA a throughput of $0.50$ cycles per instruction, one micro-operation, and execution on ports FP0/1.

Hence, for both AMD Zen~2 and AMD Zen~3, the superscalability is
2 \text{ floating-point operations per cycle per core}.\\

To determine $n_{\text{SIMD}}$, we inspect the floating-point instructions reported in the uops.info table, where instructions such as \texttt{VFMADD132PD (YMM, YMM, YMM)} appear. The presence of YMM operands indicates the use of 256-bit AVX registers, since YMM registers are defined as 256-bit wide in the AVX/AVX2 instruction set. As both AMD Zen~2 and Zen~3 execute these YMM-based instructions, they necessarily support AVX2 with 256-bit SIMD registers. A double-precision floating-point number occupies 64 bits; therefore, the number of doubles that can be processed concurrently by one SIMD instruction is

$$
n_{\text{SIMD}} = \frac{256}{64} = 4.
$$

Hence, each SIMD instruction can operate on four double-precision values in parallel.

\subsection{Performance model: A simple roofline model [16 Points]}
A (naive) roofline model provides an upper bound on the attainable performance of a kernel as a function of
its operational intensity $I$ (in Flops/Byte). For a given hardware, the attainable performance is bounded by:
\begin{itemize}
  \item a \textbf{compute ceiling} given by the peak floating-point performance $P_{\text{peak}}$ (in GFlops/s),
  \item a \textbf{bandwidth ceiling} given by $B \cdot I$, where $B$ is the sustainable memory bandwidth (in GBytes/s).
\end{itemize}
Hence the roofline bound is
$$
P(I) = \min\left(P_{\text{peak}},\; B \cdot I\right).
$$

The transition between memory-bound and compute-bound regimes occurs at the \textbf{ridge point}:
\begin{equation}
I_{\text{ridge}} = \frac{P_{\text{peak}}}{B}.
\label{eq:ridge}
\end{equation}
A kernel with $I < I_{\text{ridge}}$ is memory-bound, while a kernel with $I > I_{\text{ridge}}$ is compute-bound.\\

From the previous exercises, we have already computed the peak performance $P_{\text{peak}}$ and the sustainable memory bandwidth $B$ for both Euler VII phases. The values of the single core peak performances where
\begin{align*}
P_{\text{peak,1}} &= 41.6~\text{GFlops/s} \quad \text{(Euler VII phase 1, AMD EPYC 7H12 @ 2.6 GHz)},\\
P_{\text{peak,2}} &= 39.2~\text{GFlops/s} \quad \text{(Euler VII phase 2, AMD EPYC 7763 @ 2.45 GHz)}.
\end{align*}
\\
We use the STREAM \texttt{Triad} bandwidth as sustainable memory bandwidth, since it represents a
typical streaming workload (three arrays, two loads + one store per iteration) and is commonly used in
roofline constructions.
From our STREAM outputs, we have the following sustainable memory bandwidths:
\begin{align*}
B_{1} &= 19668.1~\text{MB/s} = 19.6681~\text{GB/s},\\
B_{2} &= 149198.6~\text{MB/s} = 14.2~\text{GB/s},
\end{align*}
where we convert MB/s to GB/s by dividing by $1000$.\\
Using Eq.\ref{eq:ridge}:
\begin{align*}
I_{\text{ridge,1}} &= \frac{P_{\text{peak,1}}}{B_1}
= \frac{41.6}{19.6681}
\approx 2.12~\text{Flops/Byte},\\
I_{\text{ridge,2}} &= \frac{P_{\text{peak,2}}}{B_2}
= \frac{39.2}{14.2}
\approx 2.76~\text{Flops/Byte}.
\end{align*}

\section{Auto-vectorization [10 points]}

\textbf{Question 1: what is data alignment and is it important for data structures to be aligned?}\\
Data alignment refers to placing an object in memory at an address that is a multiple of some power-of-two boundary (for example, 16 bytes). In the document, alignment is discussed as a key performance property for SIMD loads/stores: Intel SSE (and similarly other SIMD ISAs) prefers aligned memory references, and data movement instructions can be significantly more efficient when the data is aligned. The text also warns that using aligned data-movement instructions with incorrectly aligned addresses can even raise an exception (so alignment assertions must be correct).\\
Because of this, it is generally important that frequently accessed arrays/structures used in vectorized loops are aligned (e.g., 16-byte boundaries for SSE), especially when you want the compiler to generate efficient aligned vector loads/stores and avoid extra fix-up code.\\

\textbf{Question 2: what are some obstacles that can prevent automatic vectorization by the compiler?}\\
Several recurring patterns can make vectorization unsafe or not worthwhile, so the compiler may decide to keep scalar code. A first frequent issue is \textbf{non-contiguous memory access}: when a loop uses non-unit strides or indirect addressing (for instance, indices coming from another array), the hardware cannot easily use a single packed load, and the compiler anticipates extra gathers and inefficient memory traffic. \\
Another common blocker is the presence of \textbf{loop-carried dependencies}. Since SIMD executes multiple iterations ``together'', it effectively changes the per-iteration execution order; if the compiler cannot prove that different iterations are independent, it must conservatively assume a dependence and will often avoid vectorization.\\
Vectorization is also discouraged when the loop is not in a \textbf{canonical vector-friendly form}. Compilers prefer countable loops whose trip count is known at entry, with a single entry and a single exit, and with straight-line bodies; complex or unsupported control flow (e.g.\ \texttt{switch} statements, early exits, or other non-structured patterns) makes it harder to build a correct vector loop. Moreover, \textbf{function calls inside the loop body} frequently stop vectorization: even something as simple as printing introduces side effects and prevents reordering, unless the call is a recognized intrinsic, can be proven safe, or can be inlined.\\ Finally, \textbf{pointer aliasing} and complicated pointer expressions can force the compiler into worst-case assumptions: if two pointers might refer to overlapping memory, then loads and stores may depend on each other across iterations, and the compiler may refuse vectorization or add costly runtime checks.\\

\textbf{Question 3: is there a way to help the compiler to vectorize and how?}\\
Yes. One can increase the chances of vectorization by writing vector-friendly code and by supplying additional information that the compiler cannot safely infer. A direct way is to use \textbf{pragmas} that communicate dependence and vectorization intent: for instance, \texttt{\#pragma ivdep} requests the compiler to ignore assumed dependencies, while directives of the form \texttt{\#pragma vector ...} can specify whether the vector loop should be generated and how alignment should be treated, potentially overriding conservative profitability heuristics.\\
A second powerful aid is to reduce aliasing uncertainty with \textbf{\texttt{restrict}} (C99). When \texttt{restrict} is correct, it asserts that pointers do not overlap, so the compiler can remove conservative dependence assumptions and avoid inserting runtime alias checks. In the same spirit, the user can \textbf{communicate alignment} properties: data can be declared with explicit alignment (e.g.\ \texttt{\_\_declspec(align(...))}), and compilers also provide mechanisms to assume alignment or other conditions (e.g.\ \texttt{\_\_builtin\_assume\_aligned(a,n)} or more general assumptions via \texttt{\_\_builtin\_assume(cond)}), which may unlock aligned vector loads and reduce peeling/checking overhead. Finally, \textbf{data layout choices} matter: adopting a structure-of-arrays (SoA) layout often turns accesses into unit-stride streams, which are typically much easier and more profitable to vectorize than the scattered accesses typical of an array-of-structures (AoS) layout.\\

\textbf{Question 4: which loop optimizations are performed by the compiler to vectorize and pipeline loops?}\\
Successful vectorization is often enabled only after stronger optimization settings activate additional loop transformations that reshape the loop into a more regular form. In this context, the compiler commonly applies \textbf{loop unrolling} together with packed SIMD instruction generation: vectorization produces SIMD instructions that cover multiple scalar iterations, which is conceptually similar to unrolling, and manual unrolling is generally unnecessary if its only purpose is to ``force'' vectorization.\\
Another important transformation is \textbf{loop peeling for alignment}. By executing a small number of scalar iterations first, the compiler can reach an aligned address boundary (e.g.\ 16-byte alignment for SSE) so that the main vector loop can use aligned accesses more consistently and efficiently. Since vectorization typically targets the \emph{innermost} loop, earlier loop transformations such as \textbf{interchange, collapsing, or related restructuring effects} can change which loop becomes innermost and thus becomes the vectorization target. Overall, the compiler tries to transform the original code into a regular, countable, straight-line innermost loop and, when possible, it adds alignment-oriented restructuring so that the vectorized and pipelined version runs efficiently.\\

\textbf{Question 5: what can be done if automatic vectorization by the compiler fails or is sub-optimal?}\\
A robust approach is to start from diagnosis, then remove the cause through code restructuring, and only afterwards apply stronger directives or explicit SIMD methods. Practically, the first step is to consult \textbf{vectorization reports and diagnostics} to identify whether the loop was rejected due to dependencies, aliasing, control flow, memory access patterns, or because the compiler predicted low benefit. Based on that feedback, one can often \textbf{rewrite the loop into a more vectorizable shape}: make the trip count well-defined, keep a single entry/exit, avoid unsupported control flow, remove or move function calls out of the loop, eliminate loop-carried dependencies, and prefer unit-stride array accesses over indirect indexing or complex pointer arithmetic.\\
When correctness allows it, \textbf{adding accurate annotations} can resolve conservative assumptions: \texttt{restrict} can remove aliasing ambiguity, alignment declarations or assumptions can reduce misalignment penalties, and pragmas such as \texttt{\#pragma ivdep} or \texttt{\#pragma vector always} can steer the compiler past overly cautious dependence or profitability decisions. These mechanisms must be used carefully, since forcing aligned loads on misaligned addresses or providing incorrect dependence information can change semantics or even lead to crashes. If hints remain insufficient, \textbf{user-mandated SIMD directives} such as \texttt{\#pragma omp simd} can be used to impose vectorization semantics and typically trigger warnings if the compiler cannot generate a vector loop, while also allowing clauses to specify the intended SIMD behavior. Finally, enabling broader optimization context---for instance with \textbf{high optimization levels and interprocedural optimization}---can improve vectorization by exposing more information (e.g.\ enabling inlining and better dependence reasoning) and by applying additional transformations. If performance is still unsatisfactory, the last step is to move to \textbf{more explicit SIMD programming} (e.g.\ SIMD extensions or intrinsics), which provides tighter control and reduces reliance on compiler heuristics.

\section{Matrix multiplication optimization [30 points]}

\textbf{Task 1: Improve the loop ordering in \path{dgemm_jki.c}.}\\
The original implementation uses the loop order $i$--$j$--$k$:
\begin{lstlisting}[style=grayverbatim,language=C]
void square_dgemm(int n, double* A, double* B, double* C) {
  for (int i = 0; i < n; ++i) {
    for (int j = 0; j < n; ++j) {
      for(int k = 0; k < n; ++k) {
        C[i+j*n] += A[i+k*n] * B[k+j*n];
      }
    }
  }
}
\end{lstlisting}
This loop ordering is correct, but it performs poorly for column-major storage (indexing $i + jn$). 
In the innermost loop over $k$, the access to $A[i + k n]$ moves across different columns of $A$ with a stride of $n$, i.e., it repeatedly jumps to memory locations that are far apart. 
This limits spatial locality and makes it difficult for the cache hierarchy and hardware prefetchers to be effective. 
By contrast, $B[k + jn]$ is read contiguously in the $k$-loop (a whole column of $B$), so the main bottleneck of the naive ordering is the strided access pattern to $A$.\\

To improve locality, we reorder the loops to $j$--$k$--$i$ and hoist invariant quantities out of the innermost loop:
\begin{lstlisting}[style=grayverbatim,language=C]
void square_dgemm(int n, double* A, double* B, double* C) {
  for (int j = 0; j < n; ++j) {
    double* Ccol = C + j*n;              // C(:,j)
    for (int k = 0; k < n; ++k) {
      const double bkj = B[k + j*n];     // B(k,j) reused for all i
      const double* Acol = A + k*n;      // A(:,k)
      for (int i = 0; i < n; ++i) {
        Ccol[i] += Acol[i] * bkj;        // stride-one on C and A
      }
    }
  }
}
\end{lstlisting}

With column-major layout, full columns are contiguous in memory. For fixed $(j,k)$, the innermost loop over $i$ streams through $A(:,k)$ and updates $C(:,j)$ with \emph{stride 1} (contiguous memory) in both arrays. 
This improves cache utilization and makes prefetching more effective, since consecutive iterations access consecutive memory locations. 
Moreover, loading $B(k,j)$ once into a scalar (\texttt{bkj}) and using column pointers (\texttt{Acol}, \texttt{Ccol}) reduces redundant address computations and avoids repeatedly reloading the same element of $B$. 
The computation is unchanged, since we still perform
\[
C_{i,j} \mathrel{+}= \sum_{k=0}^{n-1} A_{i,k} B_{k,j},
\]
but with a memory-access pattern that is more favorable for the cache hierarchy and that typically facilitates SIMD vectorization in the innermost loop.\\[0.5em]

\textbf{Task 2: Implement blocking for square matrix multiplication in \path{dgemm_blocked.c}.}\\
To further increase performance, we implement \emph{blocking} (tiling) in all three loop dimensions. 
Instead of working on the full iteration space at once, we partition the indices into blocks of size $BS$ along $i$, $j$, and $k$, and compute the product block-by-block:
\begin{lstlisting}[style=grayverbatim,language=C]
void square_dgemm(int n, double* A, double* B, double* C)
{
  for (int jj = 0; jj < n; jj += BS) {
    int jmax = imin(jj + BS, n);

    for (int kk = 0; kk < n; kk += BS) {
      int kmax = imin(kk + BS, n);

      for (int ii = 0; ii < n; ii += BS) {
        int imax = imin(ii + BS, n);

        for (int j = jj; j < jmax; ++j) {
          for (int k = kk; k < kmax; ++k) {
            double bkj = B[k + j * n];
            for (int i = ii; i < imax; ++i) {
              C[i + j * n] += A[i + k * n] * bkj;
            }
          }
        }
      }
    }
  }
}
\end{lstlisting}

The outer loops \texttt{jj}, \texttt{kk}, and \texttt{ii} select the current block ranges
\[
j \in [jj, j_{\max}), \qquad 
k \in [kk, k_{\max}), \qquad 
i \in [ii, i_{\max}),
\]
and the helper \texttt{imin} ensures correct handling of boundary tiles when $n$ is not a multiple of $BS$. 
Within each block triple, the inner kernel performs the same $j$--$k$--$i$ update as in Task~1, but restricted to the current submatrices.\\

Blocking improves performance by increasing \emph{temporal locality}. 
For a fixed $(jj,kk,ii)$ triple, the algorithm repeatedly reuses the same sub-blocks of $A$ and $B$ while accumulating into the corresponding sub-block of $C$, reducing the frequency at which data must be fetched from main memory. 
Inside each block, the innermost loop still runs over $i$, so the access to $A(:,k)$ and $C(:,j)$ remains stride-1 in column-major format. 
Finally, loading \texttt{bkj = B(k,j)} once per $(j,k)$ pair provides scalar reuse and avoids redundant loads in the innermost loop.\\

We set the default block size to $BS=64$, a common baseline choice for a first cache-blocked DGEMM implementation.
With double-precision elements, a $64\times 64$ tile contains $64^2$ entries and occupies $64^2\cdot 8 \approx 32$\,KiB.
The combined footprint of the three tiles $(A,B,C)$ involved in the update is therefore about $3\cdot 32 \approx 96$\,KiB. 
This working set does not fit in L1 data cache, but it fits comfortably in the per-core L2 cache, allowing substantial reuse from L2 rather than repeatedly streaming the same data from main memory. 
The block size is kept configurable via \texttt{\#ifndef BS} so that alternative values can be tested empirically on the target architecture if further tuning is desired.\\

In figure \ref{fig:timing}, we show the performance of the naive, reordered (stride-one), blocked and BLAS implementations of DGEMM on a single core of an AMD EPYC 7763 processor. 
The naive $i$--$j$--$k$ implementation stays around a few GFLOP/s and shows large variability (occasional deep drops), consistent with poor cache behavior due to strided accesses in column-major layout.
