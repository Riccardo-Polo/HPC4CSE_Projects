\section{Computing $\pi$ with \texttt{OpenMP} [20 points]}
\subsection{Exercise 1}
In this exercise we are given a code that computes an approximation of $\pi$ using numerical integration. The code uses a simple loop to compute the sum of terms that approximate the value of $\pi$. The goal of this exercise is to parallelize the code using \texttt{OpenMP} and to optimize it for better performance.\\

In the first part of the exercise it was asked to first parallelize the given code using a naive version that protects every loop update with \texttt{critical}. Here is the code snippet of the naive version that we implemented:
\begin{lstlisting}[style=grayverbatim,escapeinside={(*@}{@*)}]
  (*@\colorbox{lightbluehighlight}{\#pragma omp parallel for}@*)
  for (uint64_t i = 0; i < N; ++i) {
    double x = (i + 0.5) * h;
    double term = 4.0 / (1.0 + x*x);

    (*@\colorbox{lightbluehighlight}{\#pragma omp critical}@*)
    pi += term;
  }
  pi *= h;

  double time = walltime() - time_start;

  int nt = omp_get_max_threads(); 
  printf("# pi N num_threads time [secs]\n");
  printf("%.15f %20"PRIu64" %3d %.8f\n", pi, N, nt, time);
  \end{lstlisting}
The output of the naive version is as follows:
\begin{lstlisting}[style=grayverbatim,escapeinside={(*@}{@*)}]
# pi N num_threads time [secs]
3.141592653590757           1000000000  64 640.70646905
\end{lstlisting}
We can see that the naive version is very slow. This is because every update to the shared variable \texttt{pi} is protected by a critical section, which causes a lot of contention and serialization among the threads. Each thread has to wait for the others to finish updating \texttt{pi}, which leads to a significant slowdown in performance.\\

In the second part in was asked to create an optimized version that accumulates locally and enters critical only
once per thread. Here is the code snippet of the optimized version that we implemented:
\begin{lstlisting}[style=grayverbatim,escapeinside={(*@}{@*)}]
  (*@\colorbox{lightbluehighlight}{\#pragma omp parallel}@*)
  {
    double sum = 0.0;

    (*@\colorbox{lightbluehighlight}{\#pragma omp for}@*)
    for (uint64_t i = 0; i < N; ++i) {
      double x = (i + 0.5) * h;
      sum += 4.0 / (1.0 + x*x);
    }

    (*@\colorbox{lightbluehighlight}{\#pragma omp critical}@*)
    pi += sum;     // once per thread
  }
  pi *= h;

  double time = walltime() - time_start;

  int nt = omp_get_max_threads(); 
  printf("# pi N num_threads time [secs]\n");
  printf("%.15f %20"PRIu64" %3d %.8f\n", pi, N, nt, time);
\end{lstlisting}
In this version we have a local variable \texttt{sum} that is private to each thread, and we only enter the critical section once per thread to update the shared variable \texttt{pi}. This reduces the contention on the critical section and allows for better performance. The output of the optimized version is as follows:
\begin{lstlisting}[style=grayverbatim,escapeinside={(*@}{@*)}]
# pi N num_threads time [secs]
3.141592653589771           1000000000  64 0.19858712
\end{lstlisting}
We can see that the optimized version is significantly faster than the naive version. The optimized version allows for better utilization of the available threads and reduces the overhead caused by the critical section.\\

We are then asked to implement a version that uses the reduction clause. Here is the code snippet of the version that uses the reduction clause:
\begin{lstlisting}[style=grayverbatim,escapeinside={(*@}{@*)}]
  (*@\colorbox{lightbluehighlight}{\#pragma omp parallel for reduction(+:pi)}@*)
#pragma omp parallel for reduction(+:sum)
  for (uint64_t i = 0; i < N; ++i) {
    double x = (i + 0.5)*h;
    sum += 4.0 / (1.0 + x*x);
  }
  pi = sum*h;
  double time = walltime() - time_start;

  int nt = omp_get_max_threads(); 
  printf("# pi N num_threads time [secs]\n");
  printf("%.15f %20"PRIu64" %3d %.8f\n", pi, N, nt, time);
\end{lstlisting}
In this version we use the \texttt{reduction} clause to automatically handle the accumulation of the variable \texttt{pi} across threads. The reduction clause takes care of creating a private copy of the variable for each thread and then combining the results at the end of the parallel region. This allows for a more concise and efficient implementation. The output of the version that uses the reduction clause is as follows:
\begin{lstlisting}[style=grayverbatim,escapeinside={(*@}{@*)}]
# pi N num_threads time [secs]
3.141592653589771           1000000000  64 0.11437800
\end{lstlisting}
We can see that the optimized version and the version that uses the reduction clause are significantly faster than the naive version. The reduction clause version is also more concise and easier to read, making it a good choice for this type of problem.\\

In the while loop, we are iterating through the orbit of the point c under the function $f(z) = z^2 + c$. The variables x and y represent the real and imaginary parts of the complex number z, respectively. The equations used in the while loop are derived from the definition of complex multiplication and addition. Specifically, the function $f(z)$ can be expressed in terms of its real and imaginary components as follows:ù
% use latex math mode to write the equations
\begin{align*}
f(z) &= z^2 + c \\
&= (x + yi)^2 + (cx + cyi) \\
&= (x^2 - y^2 + cx) + (2xy + cy)i
\end{align*}
But why does this hold also for $f_z(c)^3 , ...$? This is because the function $f(z)$ is defined recursively, and each iteration of the function applies the same transformation to the complex number z. Therefore, when we compute $f^2(z)$, we are applying the function $f$ to the result of $f(z)$, which means that we are applying the same equations for the real and imaginary parts at each iteration. This recursive nature of the function allows us to use the same equations for each iteration in the while loop, regardless of how many times we apply the function.
From this, we can see that the real part of f(z) is given by $x^2 - y^2 + cx$, and the imaginary part is given by $2xy + cy$. Therefore, in the while loop, we update the values of x and y according to these equations to compute the next point in the orbit. The loop continues until the magnitude of z (which is $\sqrt{x^2 + y^2}$) exceeds 2, indicating that the orbit is unbounded, or until we reach the maximum number of iterations, which indicates that the point c is likely to belong to the Mandelbrot set.\\
Finally, we are asked to count the total number of iterations in order to correctly compute the benchmark statistics. This is done by introducing a variable nTotalIterationsCount that accumulates the number of iterations for each point in the complex plane. This variable is incremented by n, which represents the number of iterations for the current point (i, j). By keeping track of the total number of iterations, we can compute the benchmark statistics more accurately, as it gives us a measure of the computational effort required to compute the Mandelbrot set for the given parameters.\\

\subsection{Exercise 3}
In the third part of the exercise we are asked to parallelize the Mandelbrot set code using \texttt{OpenMP}. The goal is to improve the performance of the code by utilizing multiple threads to compute the Mandelbrot set in parallel. Here is the code snippet of the parallelized version of the Mandelbrot set code using \texttt{OpenMP}:
\begin{lstlisting}[style=grayverbatim,escapeinside={(*@}{@*)}]
  int main(int argc, char **argv) {
  ppm_data_t pPpm;
  ppm_create(&pPpm, IMAGE_WIDTH, IMAGE_HEIGHT);

  double fDeltaX = (MAX_X - MIN_X) / (double)IMAGE_WIDTH;
  double fDeltaY = (MAX_Y - MIN_Y) / (double)IMAGE_HEIGHT;

  long nTotalIterationsCount = 0;

  double time_start = walltime();
  // do the calculation
  #pragma omp parallel for reduction(+:nTotalIterationsCount) schedule(dynamic)
  for (long j = 0; j < IMAGE_HEIGHT; j++) {
    double cy = MIN_Y + j * fDeltaY;

    for (long i = 0; i < IMAGE_WIDTH; i++) {
      double cx = MIN_X + i * fDeltaX;

      double x = cx;
      double y = cy;
      double x2 = x * x;
      double y2 = y * y;

      int n = 0;
      while (x2 + y2 <= 4.0 && n < MAX_ITERS) {
        y = 2.0 * x * y + cy;
        x = x2 - y2 + cx;
        x2 = x * x;
        y2 = y * y;
        n++;
      }

      nTotalIterationsCount += n;

      int c = ((long)n * 255) / MAX_ITERS;
      ppm_plot(&pPpm, i, j, c, c, c);
    }
  }
  double time_end = walltime();
  \end{lstlisting}

The total number of iterations is slightly higher in the parallel version, which could be due to differences in the order of execution and how the iterations are distributed among the threads. The average time per pixel and average time per iteration are also significantly reduced in the parallel version, indicating that the computation is much faster when utilizing multiple threads. The iterations per second and MFlop/s metrics show a dramatic increase in performance, with the parallel version achieving 1.69429e+10 iterations per second and 135543 MFlop/s compared to 3.4352e+08 iterations per second and 2748.16 MFlop/s in the serial version. This performance improvement can be attributed to the ability of \texttt{OpenMP} to effectively utilize the available CPU cores, allowing for concurrent execution of the computations required to determine whether each point belongs to the Mandelbrot set. By distributing the workload across multiple threads, the parallel version can significantly reduce the time required to compute the Mandelbrot set, especially for larger image sizes and higher iteration counts.
