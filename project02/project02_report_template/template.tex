\section{Computing $\pi$ with \texttt{OpenMP} [20 points]}
\subsection{Exercise 1}
In this exercise we are given a code that computes an approximation of $\pi$ using numerical integration. The code uses a simple loop to compute the sum of terms that approximate the value of $\pi$. The goal of this exercise is to parallelize the code using \texttt{OpenMP} and to optimize it for better performance.\\

In the first part of the exercise it was asked to first parallelize the given code using a naive version that protects every loop update with \texttt{critical}. Here is the code snippet of the naive version that we implemented:
\begin{lstlisting}[style=grayverbatim,escapeinside={(*@}{@*)}]
  (*@\colorbox{lightbluehighlight}{\#pragma omp parallel for}@*)
  for (uint64_t i = 0; i < N; ++i) {
    double x = (i + 0.5) * h;
    double term = 4.0 / (1.0 + x*x);

    (*@\colorbox{lightbluehighlight}{\#pragma omp critical}@*)
    pi += term;
  }
  pi *= h;

  double time = walltime() - time_start;

  int nt = omp_get_max_threads(); 
  printf("# pi N num_threads time [secs]\n");
  printf("%.15f %20"PRIu64" %3d %.8f\n", pi, N, nt, time);
  \end{lstlisting}
The output of the naive version is as follows:
\begin{lstlisting}[style=grayverbatim,escapeinside={(*@}{@*)}]
# pi N num_threads time [secs]
3.141592653590757           1000000000  64 640.70646905
\end{lstlisting}
We can see that the naive version is very slow. This is because every update to the shared variable \texttt{pi} is protected by a critical section, which causes a lot of contention and serialization among the threads. Each thread has to wait for the others to finish updating \texttt{pi}, which leads to a significant slowdown in performance.\\

In the second part in was asked to create an optimized version that accumulates locally and enters critical only
once per thread. Here is the code snippet of the optimized version that we implemented:
\begin{lstlisting}[style=grayverbatim,escapeinside={(*@}{@*)}]
  (*@\colorbox{lightbluehighlight}{\#pragma omp parallel}@*)
  {
    double sum = 0.0;

    (*@\colorbox{lightbluehighlight}{\#pragma omp for}@*)
    for (uint64_t i = 0; i < N; ++i) {
      double x = (i + 0.5) * h;
      sum += 4.0 / (1.0 + x*x);
    }

    (*@\colorbox{lightbluehighlight}{\#pragma omp critical}@*)
    pi += sum;     // once per thread
  }
  pi *= h;

  double time = walltime() - time_start;

  int nt = omp_get_max_threads(); 
  printf("# pi N num_threads time [secs]\n");
  printf("%.15f %20"PRIu64" %3d %.8f\n", pi, N, nt, time);
\end{lstlisting}
In this version we have a local variable \texttt{sum} that is private to each thread, and we only enter the critical section once per thread to update the shared variable \texttt{pi}. This reduces the contention on the critical section and allows for better performance. The output of the optimized version is as follows:
\begin{lstlisting}[style=grayverbatim,escapeinside={(*@}{@*)}]
# pi N num_threads time [secs]
3.141592653589771           1000000000  64 0.19858712
\end{lstlisting}
We can see that the optimized version is significantly faster than the naive version. The optimized version allows for better utilization of the available threads and reduces the overhead caused by the critical section.\\

We are then asked to implement a version that uses the reduction clause. Here is the code snippet of the version that uses the reduction clause:
\begin{lstlisting}[style=grayverbatim,escapeinside={(*@}{@*)}]
  (*@\colorbox{lightbluehighlight}{\#pragma omp parallel for reduction(+:pi)}@*)
#pragma omp parallel for reduction(+:sum)
  for (uint64_t i = 0; i < N; ++i) {
    double x = (i + 0.5)*h;
    sum += 4.0 / (1.0 + x*x);
  }
  pi = sum*h;
  double time = walltime() - time_start;

  int nt = omp_get_max_threads(); 
  printf("# pi N num_threads time [secs]\n");
  printf("%.15f %20"PRIu64" %3d %.8f\n", pi, N, nt, time);
\end{lstlisting}
In this version we use the \texttt{reduction} clause to automatically handle the accumulation of the variable \texttt{pi} across threads. The reduction clause takes care of creating a private copy of the variable for each thread and then combining the results at the end of the parallel region. This allows for a more concise and efficient implementation. The output of the version that uses the reduction clause is as follows:
\begin{lstlisting}[style=grayverbatim,escapeinside={(*@}{@*)}]
# pi N num_threads time [secs]
3.141592653589771           1000000000  64 0.11437800
\end{lstlisting}
We can see that the optimized version and the version that uses the reduction clause are significantly faster than the naive version. The reduction clause version is also more concise and easier to read, making it a good choice for this type of problem.\\

\section{The Mandelbrot set  using \texttt{OpenMP} [20 points]}
\subsection{Exercise 1 and 2}
Here we are asked to complete the serial version of the Mandelbrot set code in the missing code part and to count the total number of iterations in order to correctly compute the benchmark statistics.\\
In the following code snippet we show the completed version of the serial code for computing the Mandelbrot set:
\begin{lstlisting}[style=grayverbatim,escapeinside={(*@}{@*)}]
double time_start = walltime();
  // do the calculation
  cy = MIN_Y;
  for (j = 0; j < IMAGE_HEIGHT; j++) {
    cx = MIN_X;
    for (i = 0; i < IMAGE_WIDTH; i++) {
      x = cx;
      y = cy;
      x2 = x * x;
      y2 = y * y;
      // compute the orbit z, f(z), f^2(z), f^3(z), ...
      // count the iterations until the orbit leaves the circle |z|=2.
      // stop if the number of iterations exceeds the bound MAX_ITERS.
      int n = 0;
      
      while (x2 + y2 <= 4.0 \&\& n < MAX\_ITERS) { 
        y = 2.0 * x * y + cy; 
        x = x2 - y2 + cx; 
        x2 = x * x; 
        y2 = y * y; 
        n++; 
      }
       nTotalIterationsCount += n; 
      // plot the number of iterations at point (i, j)
      int c = ((long)n * 255) / MAX_ITERS;
      ppm_plot(&pPpm, i, j, c, c, c);
      cx += fDeltaX;
  }
    cy += fDeltaY;
  }
  double time_end = walltime();
\end{lstlisting}
In the while loop, we are iterating through the orbit of the point c under the function $f(z) = z^2 + c$. The variables x and y represent the real and imaginary parts of the complex number z, respectively. The equations used in the while loop are derived from the definition of complex multiplication and addition. Specifically, the function $f(z)$ can be expressed in terms of its real and imaginary components as follows:ù
% use latex math mode to write the equations
\begin{align*}
f(z) &= z^2 + c \\
&= (x + yi)^2 + (cx + cyi) \\
&= (x^2 - y^2 + cx) + (2xy + cy)i
\end{align*}
But why does this hold also for $f_z(c)^3 , ...$? This is because the function $f(z)$ is defined recursively, and each iteration of the function applies the same transformation to the complex number z. Therefore, when we compute $f^2(z)$, we are applying the function $f$ to the result of $f(z)$, which means that we are applying the same equations for the real and imaginary parts at each iteration. This recursive nature of the function allows us to use the same equations for each iteration in the while loop, regardless of how many times we apply the function.
From this, we can see that the real part of f(z) is given by $x^2 - y^2 + cx$, and the imaginary part is given by $2xy + cy$. Therefore, in the while loop, we update the values of x and y according to these equations to compute the next point in the orbit. The loop continues until the magnitude of z (which is $\sqrt{x^2 + y^2}$) exceeds 2, indicating that the orbit is unbounded, or until we reach the maximum number of iterations, which indicates that the point c is likely to belong to the Mandelbrot set.\\
Finally, we are asked to count the total number of iterations in order to correctly compute the benchmark statistics. This is done by introducing a variable nTotalIterationsCount that accumulates the number of iterations for each point in the complex plane. This variable is incremented by n, which represents the number of iterations for the current point (i, j). By keeping track of the total number of iterations, we can compute the benchmark statistics more accurately, as it gives us a measure of the computational effort required to compute the Mandelbrot set for the given parameters.\\

The goal is to improve the performance of the code by utilizing multiple threads to compute the Mandelbrot set in parallel. Here is the code snippet of the parallelized version of the Mandelbrot set code using \texttt{OpenMP}:
\begin{lstlisting}[style=grayverbatim,escapeinside={(*@}{@*)}]
  int main(int argc, char **argv) {
  ppm_data_t pPpm;
  ppm_create(&pPpm, IMAGE_WIDTH, IMAGE_HEIGHT);

  double fDeltaX = (MAX_X - MIN_X) / (double)IMAGE_WIDTH;
  double fDeltaY = (MAX_Y - MIN_Y) / (double)IMAGE_HEIGHT;

  long nTotalIterationsCount = 0;

  double time_start = walltime();
  // do the calculation
  #pragma omp parallel for reduction(+:nTotalIterationsCount) schedule(dynamic)
  for (long j = 0; j < IMAGE_HEIGHT; j++) {
    double cy = MIN_Y + j * fDeltaY;

    for (long i = 0; i < IMAGE_WIDTH; i++) {
      double cx = MIN_X + i * fDeltaX;

      double x = cx;
      double y = cy;
      double x2 = x * x;
      double y2 = y * y;

      int n = 0;
      while (x2 + y2 <= 4.0 && n < MAX_ITERS) {
        y = 2.0 * x * y + cy;
        x = x2 - y2 + cx;
        x2 = x * x;
        y2 = y * y;
        n++;
      }

      nTotalIterationsCount += n;

      int c = ((long)n * 255) / MAX_ITERS;
      ppm_plot(&pPpm, i, j, c, c, c);
    }
  }
  double time_end = walltime();
  \end{lstlisting}

\section{Bug hunt [10 points]}
\subsection{File 1:   \texttt{omp\_bug1.c}}

The program attempts to parallelize the loop that computes
\[
c[i] = a[i] + b[i]
\]
using the OpenMP \texttt{parallel for} construct. However, the code contains a
syntax error that prevents compilation and also reflects a conceptual misuse
of the directive.

The first problem is related to the use of the OpenMP directive
\texttt{\#pragma omp parallel for}. This combined directive creates a parallel
region and distributes the iterations of the following loop among the threads.
For this reason, the directive must be followed \emph{immediately} by a
\texttt{for} loop. In the program, however, the directive is followed by a
compound block:

\begin{lstlisting}[style=grayverbatim,escapeinside={(*@}{@*}]
#pragma omp parallel for shared(a, b, c, chunk) private(i, tid) \
            schedule(static, chunk)
{
  tid = omp_get_thread_num();
  for (i = 0; i < N; i++) {
    ...
  }
}
\end{lstlisting}

This structure is invalid because the \texttt{parallel for} directive must be
attached directly to the loop it parallelizes.

The second issue concerns the variable \texttt{tid}. The programmer wants to
print which thread executes each iteration, but the statement

\begin{lstlisting}[style=grayverbatim,escapeinside={(*@}{@*}]
tid = omp_get_thread_num();
\end{lstlisting}

is placed outside the loop that the directive is supposed to parallelize.
Because the directive requires the loop to appear immediately after it, this
statement breaks the required structure of the construct.

To fix the problem, the loop must appear directly after the OpenMP directive.
The thread identifier should instead be retrieved inside the loop body (or
inside a parallel region if the \texttt{parallel} and \texttt{for} constructs
are separated). In this way, each thread can correctly obtain its ID and print
the information for the iterations it executes.

\subsection{File 2: \texttt{omp\_bug2.c}}
The program contains errors related to the incorrect handling of \texttt{shared} and \texttt{private} variables inside the OpenMP parallel region.

The variables \texttt{tid}, \texttt{i}, and \texttt{total} are declared outside the \texttt{\#pragma omp parallel} region and therefore are \emph{shared} by default among all threads. This leads to race conditions and incorrect program behaviour.

First, the variable \texttt{tid} is shared, although each thread assigns its own thread ID through
\begin{lstlisting}[style = grayverbatim,escapeinside={(*@}{@*}]
tid = omp_get_thread_num();
\end{lstlisting}


Since all threads write to the same memory location, the value of \texttt{tid} can be overwritten by other threads. As a result, the value stored in \texttt{tid} is not guaranteed to correspond to the correct thread.

A more serious problem concerns the variable \texttt{total}. Inside the parallel region the code initializes
\begin{lstlisting}[style=grayverbatim]
total = 0.0;
\end{lstlisting}
and then performs a parallel loop
\begin{lstlisting}[style=grayverbatim]
#pragma omp for schedule(dynamic, 10)
for (i = 0; i < 1000000; i++)
    total = total + i * 1.0;
\end{lstlisting}
Because \texttt{total} is shared, all threads update the same variable concurrently. This produces a race condition and the resulting sum is incorrect and non-deterministic. Moreover, each thread resets the shared variable to zero before the loop, which introduces additional data races.

Finally, the statement
\begin{lstlisting}[style=grayverbatim]
printf("Thread %d is done! Total= %e\n", tid, total);
\end{lstlisting}
is located outside the parallel region. Consequently, it is executed only once by the main thread, even though the programmer likely intended each thread to report completion.

The problem can be fixed by ensuring correct data scoping. The variable \texttt{tid} should be declared \emph{private} so that each thread keeps its own thread identifier. The summation should be implemented using an OpenMP \texttt{reduction} on \texttt{total}, which safely combines the partial sums computed by different threads. If each thread should report completion, the corresponding \texttt{printf} statement should be placed inside the parallel region.

\subsection{File 3: \texttt{omp\_bug3.c}}
The main problem in this program is the incorrect use of the \texttt{barrier} directive inside the function \texttt{print\_results}. In OpenMP, a barrier must be encountered by \emph{all} threads of the team, or by none of them. Here, however, \texttt{print\_results} is called only by the threads that actually execute one of the two \texttt{sections}. Since there are only two sections, at most two threads will enter the function, while the other threads in the parallel region will skip it entirely. As a consequence, only a subset of threads reaches the barrier placed at the end of \texttt{print\_results}, which leads to an illegal synchronization pattern and can cause the program to hang at run time.

A second issue is that the intent of having ``clean output'' is only partially achieved. The \texttt{critical} region correctly prevents the printed array contents from being interleaved, so the output of one thread is kept together. However, the statement
\begin{lstlisting}[style=grayverbatim,escapeinside={(*@}{@*}]
printf("Thread %d done and synchronized.\n", tid);
\end{lstlisting}
is placed \emph{after} the barrier and outside the critical region, so even if the barrier were legal, these messages could still appear in overlapping or non-deterministic order with respect to other threads' output.

There is also a conceptual inconsistency in combining \texttt{sections nowait} with the later synchronization logic. The \texttt{nowait} clause removes the implicit barrier at the end of the \texttt{sections} construct, but then the code tries to enforce synchronization manually inside \texttt{print\_results} using a barrier, which is not valid for the reason explained above. If synchronization after the sections is desired, it should be done at a point that is reached by every thread in the parallel region.

To fix the code, the barrier inside \texttt{print\_results} should be removed. Any barrier should instead be placed in the main parallel region, at a location where all threads are guaranteed to encounter it. Moreover, if the programmer wants all output messages to appear cleanly and without overlap, every printing operation that must remain grouped should be enclosed in the same \texttt{critical} region, or alternatively all printing should be reorganized so that only one thread prints at a time in a controlled way. Finally, if synchronization at the end of the \texttt{sections} construct is required, the simplest correction is to remove the \texttt{nowait} clause and rely on the implicit barrier provided by \texttt{sections}.

In summary, the critical bug is the illegal barrier inside \texttt{print\_results}, because not all threads execute that function. This may cause a deadlock. The proper fix is to move synchronization points outside the function and ensure that every barrier is reached by all threads in the team.

\subsection{File 4: \texttt{omp\_bug4.c}}

The problem is caused by \emph{stack overflow} in the OpenMP region. The key issue is that the array
\[
\texttt{real(8) :: e\_in(nmax)}
\]
is declared inside the main program and the parallel region uses
\[
\texttt{!\$omp parallel default(firstprivate)}.
\]
Because of \texttt{firstprivate}, each OpenMP thread receives its own private copy of \texttt{e\_in}. Since
\[
n_{\max}=202000,
\]
this array alone occupies about
\[
202000 \times 8 \approx 1.6\ \text{MB}
\]
per thread. These private copies are typically placed on the thread stack. If the available stack size is too small, entering the parallel region causes a segmentation fault.

There is a second large object involved:
\[
\texttt{double complex :: eTDSE(ntmax)}
\]
inside the module, declared as
\[
\texttt{!\$omp threadprivate(eTDSE)}.
\]
This means that each thread also has its own copy of \texttt{eTDSE}. A \texttt{double complex} element usually requires 16 bytes, so this array takes about
\[
202000 \times 16 \approx 3.2\ \text{MB}
\]
per thread. Therefore, with OpenMP enabled, the memory required per thread becomes quite large. The crash appears only when both arrays are effectively used in the parallel region, which is why removing one of the \texttt{print} statements may make the program run.\\

The code is not wrong from a syntax point of view, but it is wrong from a memory-management perspective. The main mistake is using \texttt{default(firstprivate)} in a region where a large local array such as \texttt{e\_in} exists. This forces unnecessary duplication of a large array on each thread stack. In addition, \texttt{threadprivate(eTDSE)} also creates one copy per thread, which further increases memory pressure.\\
So the real bug is the \emph{combination of large thread-local data and insufficient thread stack size}.\\

A first possible fix is to avoid making \texttt{e\_in} firstprivate if this is not needed. Since the array is only read in the loop, it should be shared instead of private. In practice, one should replace the overly broad
\[
\texttt{default(firstprivate)}
\]
with a more careful data-sharing specification, for example making \texttt{e\_in} shared.

A second fix is to increase the stack size. On Unix-like systems this can be done for the main thread with
\[
\texttt{ulimit -s}
\]
and for OpenMP worker threads with environment variables such as \texttt{OMP\_STACKSIZE}. With Intel OpenMP, \texttt{KMP\_STACKSIZE} can also be used. This does not remove the underlying inefficiency, but it may prevent the crash.

Another possible improvement is to avoid storing such large arrays on the stack. Allocatable arrays or heap-based storage are often preferable for large data structures in OpenMP programs. This reduces the risk of stack overflow and makes memory usage more controllable.\\

The segmentation fault is caused by insufficient stack memory, not by an invalid OpenMP construct. The array \texttt{e\_in} becomes private to each thread because of \texttt{default(firstprivate)}, and \texttt{eTDSE} is also duplicated because it is \texttt{threadprivate}. The resulting per-thread memory usage is too large for the available stack. The proper fix is to avoid unnecessary privatization of large arrays, and, if needed, increase the OpenMP thread stack size or move the data to heap allocation.

\subsection{File 5: \texttt{omp\_bug5.c}}

The main bug in this program is a \textbf{deadlock caused by inconsistent lock ordering}.  
The two \texttt{sections} acquire the two locks in opposite order. In the first section the thread acquires \texttt{locka} and then \texttt{lockb}, while in the second section the order is reversed: the thread first acquires \texttt{lockb} and then \texttt{locka}.

This can lead to a classic deadlock situation. For example, Thread~0 may acquire \texttt{locka} while Thread~1 acquires \texttt{lockb}. Afterwards, Thread~0 waits for \texttt{lockb}, which is already held by Thread~1, and Thread~1 waits for \texttt{locka}, which is held by Thread~0. Since each thread is waiting for a lock owned by the other one, neither thread can proceed and the program blocks indefinitely.

There is also a second issue related to the loop variable \texttt{i}. The variable \texttt{i} is declared outside the parallel region and is therefore \textbf{shared} by default. Since both sections execute concurrently and use the same loop variable, this creates a \textbf{data race}. Each thread should instead operate on its own private copy of the loop index.

To fix the program, the locking order must be made consistent. All threads should acquire multiple locks in the same global order (for instance always acquiring \texttt{locka} before \texttt{lockb}). This removes the circular wait condition and therefore prevents the deadlock. Another possible improvement is to redesign the algorithm so that nested locking is not required; for example, the arrays could be initialized first, followed by a synchronization point, and only afterwards the addition operations could be performed. Finally, the loop variable \texttt{i} should be made \textbf{private} inside the parallel region or declared locally inside each section so that each thread uses its own independent copy.
