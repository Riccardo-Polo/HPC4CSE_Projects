\subsection{Domain decomposition [10 Points]}
Here we are asked to design a domain decomposition strategy that is compatible with any square grid size and any number of MPI processes while considering load balancing, communication overhead and computational efficiency. We were suggested to look at the short discussion in \cite[Sec. 10.4.1]{hager2010hpc}.\\
We can first notice that for a subdomain of size $n_x \times n_y$ we have a total computation of $n_x \cdot n_y$ while the halo exchange requires $2 \cdot (n_x + n_y)$ communicated boundary points. For a fixed local area $A = n_x n_y$, the arithmetic-geometric mean inequality gives
\[
n_x + n_y \ge 2\sqrt{n_x n_y} = 2\sqrt{A},
\]
with equality when $n_x = n_y$. Therefore, for a fixed local area, communication is minimized when the rectangle is as close to a square as possible. Indeed in \cite[Sec. 10.4.1]{hager2010hpc} they suggest that we have to avoid slab decomposition. For example, if you split only in $x$, each process has a long thin strip. It computes fewer points, but the communicated boundary length stays large. A 2D Cartesian decomposition is better because both $n_x$ and $n_y$ decrease as the number of MPI processes increases.

\begin{lstlisting}[style=grayverbatim,label={lst:subdomain_init},caption={Initialization of the sub-domain}]
void SubDomain::init(int mpi_rank, int mpi_size,
                     Discretization& discretization) {
    // Determine the number of sub-domains in the x and y dimensions
    //       using MPI_Dims_create
    int dims[2] = {0, 0};
    MPI_Dims_create(mpi_size,2,dims);
    ndomy = dims[0];
    ndomx = dims[1];

    // Create a 2D non-periodic Cartesian topology using MPI_Cart_create
    int periods[2] = {0, 0};
    MPI_Cart_create(MPI_COMM_WORLD,2,dims,periods,0,&comm_cart);

    // Retrieve coordinates of the rank in the topology using
    // MPI_Cart_coords
    int coords[2] = {0, 0};
    MPI_Cart_coords(comm_cart, mpi_rank , 2 , coords);
    domy = coords[0] + 1;
    domx = coords[1] + 1;

    // Set neighbours for all directions using MPI_Cart_shift
    MPI_Cart_shift(comm_cart, 0 , 1 , &neighbour_south, &neighbour_north);
    MPI_Cart_shift(comm_cart, 1 , 1 , &neighbour_west, &neighbour_east);

    // get Cartesian coordinates, but use 0-based versions for computations
    int coord_y = coords[0];
    int coord_x = coords[1];

    // distribute grid points in x direction
    int base_nx = discretization.nx / ndomx;
    int rem_x   = discretization.nx % ndomx;

    nx = base_nx + (coord_x < rem_x ? 1 : 0);

    startx = coord_x * base_nx + std::min(coord_x, rem_x);
    endx   = startx + nx - 1;

    // distribute grid points in y direction
    int base_ny = discretization.nx / ndomy;
    int rem_y   = discretization.nx % ndomy;

    ny = base_ny + (coord_y < rem_y ? 1 : 0);

    starty = coord_y * base_ny + std::min(coord_y, rem_y);
    endy   = starty + ny - 1;

    // get total number of grid points in this sub-domain
    N = nx*ny;

    rank = mpi_rank;
    size = mpi_size;
}
\end{lstlisting}
This code splits the global $N \times N$ grid into a 2D Cartesian process grid. The total number of points in each direction is divided by the number of processes along that axis, giving a base block size (\texttt{base\_nx} and \texttt{base\_ny}). The remainders (\texttt{rem\_x} and \texttt{rem\_y}) are assigned one extra grid point to the first ranks in each direction, so the subdomains differ in size by at most one cell. The expressions for \texttt{startx}, \texttt{endx}, \texttt{starty}, and \texttt{endy} then compute the global index range of each local block using prefix sums. This keeps the workload balanced while still covering the full domain without overlaps or gaps.

\subsection{Linear algebra kernels [5 Points]}
The linear algebra kernels were adapted to the MPI domain-decomposed setting.
Most vector operations, such as \texttt{hpc\_fill}, \texttt{hpc\_axpy},
\texttt{hpc\_scale}, \texttt{hpc\_lcomb}, \texttt{hpc\_copy},
\texttt{hpc\_scaled\_diff}, and \texttt{hpc\_add\_scaled\_diff}, remain local.
Each MPI process stores only its own subdomain, and these routines operate
independently on the local entries.\\

The only kernels requiring MPI communication are the reduction operations
\texttt{hpc\_dot} and \texttt{hpc\_norm2}. In both cases, each process first
computes its local contribution. The local results are then combined across all
MPI ranks using \texttt{MPI\_Allreduce} with \texttt{MPI\_SUM}. This is necessary
because scalar products and norms are global quantities over the full
distributed vector. In listing \ref{lst:hpc_dot} we can see the implementation of the dot product. Each process computes the local dot product of its subdomain, and then we call \texttt{MPI\_Allreduce} to sum up the local results into a global result. The same pattern is used for the 2-norm in listing \ref{lst:hpc_norm2}, where we compute the local sum of squares and then take the square root of the global sum.

\begin{lstlisting}[style=grayverbatim,label={lst:hpc_dot},caption={MPI parallel implementation of the dot product}]
double hpc_dot(Field const& x, Field const& y) {
    int N = y.length();
    double result = 0;
    // compute local result
    for (int i = 0; i < N; i++) {
        result += x[i] * y[i];
    }

    double global_result = 0.0;
    MPI_Allreduce(&result, &global_result, 1, MPI_DOUBLE, MPI_SUM,
                  data::domain.comm_cart);

    return global_result;
}
\end{lstlisting}

\begin{lstlisting}[style=grayverbatim,label={lst:hpc_norm2},caption={MPI parallel implementation of the 2-norm}]
double hpc_norm2(Field const& x) {
    int N = x.length();
    double result = 0;
    // compute local result
    for (int i = 0; i < N; i++) {
        result += x[i] * x[i];
    }

    double global_result = 0.0;
    MPI_Allreduce(&result, &global_result, 1, MPI_DOUBLE, MPI_SUM,
                  data::domain.comm_cart);

    return sqrt(global_result);
}
\end{lstlisting}

The conjugate-gradient solver \texttt{hpc\_cg} did not require structural
changes, since it calls the linear algebra kernels internally. Once the dot
products and norms are made global, the CG coefficients are computed
consistently across all ranks.



\subsection{The diffusion stencil: Ghost cells exchange [10 Points]}
Here we are asked to implement the ghost cell exchange between neighboring processes using non-
blocking point-to-point communication with the objective to overlap computation and communication.\\
In listing \ref{lst:ghost_exchange} we provide a piece of the \texttt{diffusion} method where we tried to implement the ghost cell exchange.
\begin{lstlisting}[style=grayverbatim,label={lst:ghost_exchange},caption={Ghost cell exchange using non-blocking point-to-point communication}]
    int countx = nx ; // number of interior points in x for rows
    int county = ny ; // number of interior points in y for columns

    // temporary send buffers for columns (non-contiguous in Field)
    std::vector<double> sendW(county), sendE(county);
    for (int j = 0; j < county; ++j) {
        sendW[j] = s_new(0, j);         // left interior column
        sendE[j] = s_new(nx-1, j);     // right interior column
    }

    MPI_Request reqs[8];
    int reqcnt = 0;

    // Post non-blocking receives into the boundary arrays (contiguous)
    if (domain.neighbour_north != MPI_PROC_NULL) {
        MPI_Irecv(&bndN[0], countx, MPI_DOUBLE, domain.neighbour_north, 0,
                  domain.comm_cart, &reqs[reqcnt++]);
    }
    if (domain.neighbour_south != MPI_PROC_NULL) {
        MPI_Irecv(&bndS[0], countx, MPI_DOUBLE, domain.neighbour_south, 0,
                  domain.comm_cart, &reqs[reqcnt++]);
    }
    if (domain.neighbour_west != MPI_PROC_NULL) {
        MPI_Irecv(&bndW[0], county, MPI_DOUBLE, domain.neighbour_west, 1,
                  domain.comm_cart, &reqs[reqcnt++]);
    }
    if (domain.neighbour_east != MPI_PROC_NULL) {
        MPI_Irecv(&bndE[0], county, MPI_DOUBLE, domain.neighbour_east, 1,
                  domain.comm_cart, &reqs[reqcnt++]);
    }

    // Post non-blocking sends
    if (domain.neighbour_north != MPI_PROC_NULL) {
        MPI_Isend(&s_new(0, ny-1), countx, MPI_DOUBLE, domain.neighbour_north, 0,
                  domain.comm_cart, &reqs[reqcnt++]);
    }
    if (domain.neighbour_south != MPI_PROC_NULL) {
        MPI_Isend(&s_new(0, 0), countx, MPI_DOUBLE, domain.neighbour_south, 0,
                  domain.comm_cart, &reqs[reqcnt++]);
    }
    if (domain.neighbour_west != MPI_PROC_NULL) {
        MPI_Isend(sendW.data(), county, MPI_DOUBLE, domain.neighbour_west, 1,
                  domain.comm_cart, &reqs[reqcnt++]);
    }
    if (domain.neighbour_east != MPI_PROC_NULL) {
        MPI_Isend(sendE.data(), county, MPI_DOUBLE, domain.neighbour_east, 1,
                  domain.comm_cart, &reqs[reqcnt++]);
    }

    // Wait for all posted requests
    if (reqcnt > 0) MPI_Waitall(reqcnt, reqs, MPI_STATUSES_IGNORE);
\end{lstlisting}

This implementation exchanges the halo cells by separating the communication
into two directions. The north and south boundaries can be sent directly,
because the corresponding rows are contiguous in memory, while the west and
east boundaries require temporary buffers since the columns of the local field
are not stored contiguously. For this reason, first we pack the left and
right interior columns into \texttt{sendW} and \texttt{sendE}, and then posts
non-blocking receives and sends for all available neighbors. Using
\texttt{MPI\_Irecv} and \texttt{MPI\_Isend} allows the communication to
progress while the interior part of the stencil can still be computed, which is
the main mechanism for overlapping communication and computation. The tags
\texttt{0} and \texttt{1} distinguish row and column messages, and the checks
against \texttt{MPI\_PROC\_NULL} ensure that boundary processes simply skip
the missing neighbors. Finally, \texttt{MPI\_Waitall} guarantees that all
halo exchanges are complete before the updated ghost layers are used in the
next stencil step.

\subsection{Implement parallel I/O [10 Points]}
By looking at the file \texttt{mpio\_io.c} we were asked to implement the output of the computed solution with MPI-I/O.\\
This was done by completing the function \texttt{write\_binary} in \texttt{main.cpp} as shown in listing \ref{lst:mpio_io}.
\begin{lstlisting}[style=grayverbatim,label={lst:mpio_io},caption={MPI-IO implementation of the output}]
void write_binary(std::string fname, Field &u, SubDomain &domain,
                  Discretization &options) {
    MPI_File file;
    MPI_File_open(MPI_COMM_WORLD, fname.c_str(),
                  MPI_MODE_CREATE | MPI_MODE_WRONLY, MPI_INFO_NULL, &file);

    // global sizes (full global grid)
    int sizes[2] = { options.nx, options.nx };
    // local subarray sizes
    int subsizes[2] = { domain.ny, domain.nx };
    // start indices in the global array
    int starts[2] = { domain.starty, domain.startx };

    MPI_Datatype filetype;
    MPI_Type_create_subarray(2, sizes, subsizes, starts, MPI_ORDER_C,
                             MPI_DOUBLE, &filetype);
    MPI_Type_commit(&filetype);

    MPI_Offset disp = 0;
    MPI_File_set_view(file, disp, MPI_DOUBLE, filetype, "native", MPI_INFO_NULL);

    // write the local data collectively
    MPI_File_write_all(file, u.data(), domain.N, MPI_DOUBLE, MPI_STATUS_IGNORE);

    MPI_Type_free(&filetype);
    MPI_File_close(&file);
}
\end{lstlisting}
The implementation uses MPI-IO to write the distributed field data into a single binary file. Each process defines a subarray datatype that describes its local portion of the global grid, and then collectively writes its data using \texttt{MPI\_File\_write\_all}. The use of \texttt{MPI\_Type\_create\_subarray} allows each process to specify its unique offset and size within the global array, enabling a seamless parallel output without the need for gathering data on a single rank.

\subsection{Sum of ranks: MPI collectives [5 Points]}
We were asked to implement the sum of ranks using MPI for Python’s collective communication method.
\subsubsection{Pickle based}
In the first case we had to use pickle-based communication of generic Python objects, i.e. the all-lowercase methods.\\
In listing \ref{lst:sum_ranks_pickle} we can see the implementation of the sum of ranks using the pickle-based collective communication method.
\begin{lstlisting}[style=grayverbatim,label={lst:sum_ranks_pickle},caption={Sum of ranks using pickle-based collective communication}]
from mpi4py import MPI

# get comm, size, rank & host name
comm = MPI.COMM_WORLD
size = comm.Get_size()
rank = comm.Get_rank()
proc = MPI.Get_processor_name()

total = rank
current_value = rank

for _ in range(size - 1):
    received_value = comm.sendrecv(
        current_value,
        dest=(rank + 1) % size,
        sendtag=0,
        source=(rank - 1 + size) % size,
        recvtag=0,
    )
    total += received_value
    current_value = received_value

print(f"Sum is {total} on processor {proc}, rank {rank} out of {size} "
      f"processes")
\end{lstlisting}
The implementation follows a ring communication pattern. Each MPI process starts from its own
rank, stored both in \texttt{total} and in \texttt{current\_value}. The variable \texttt{total}
is the local accumulator, while \texttt{current\_value} is the value that is forwarded around the
ring. At each iteration, process \texttt{rank} sends its current value to the process
\texttt{(rank + 1) \% size} and receives a value from the process
\texttt{(rank - 1 + size) \% size}. The modulo operation implements the periodicity of the ring:
the last rank sends to rank zero, and rank zero receives from the last rank.\\

The communication is performed with the lower-case mpi4py routine \texttt{comm.sendrecv}. Lower-case
mpi4py methods operate on generic Python objects. Therefore, the integer sent by each process is first
serialized by Python using pickle, transmitted through MPI, and then reconstructed on the receiving
side. This makes the interface very convenient because no explicit buffer or datatype has to be specified.
However, this convenience introduces an additional serialization overhead, which can become relevant
for larger data structures.\\

The use of \texttt{sendrecv} is important for correctness. If the code used separate blocking
\texttt{send} and \texttt{recv} calls, all processes could potentially wait for a matching receive,
leading to a deadlock depending on the MPI implementation and message size. The routine
\texttt{sendrecv} combines the send and receive operations into a single MPI call, allowing all ranks
to exchange data with their two neighbours safely.\\After one iteration, every process has received the rank value of its left neighbour. After two
iterations, it has received the rank value two positions away, and so on. Consequently, after
\texttt{size - 1} iterations, every process has received all other ranks exactly once. Since each
process also initialized \texttt{total} with its own rank, the final value of \texttt{total} is the
sum of all ranks,
\[
\sum_{r=0}^{\texttt{size}-1} r
=
\frac{\texttt{size}(\texttt{size}-1)}{2}.
\]

\texttt{size = 8}, therefore the expected result is
\[

\]
Every rank prints \texttt{Sum is 28}, showing that the ring communication has circulated all rank

\subsubsection{Direct array data communication}
In the second case we had to use direct array data communication with the all-uppercase methods, i.e. the MPI methods that directly handle array data without pickling.\\
In listing \ref{lst:sum_ranks_direct} we can see the implementation of the sum of ranks using direct array data communication.
\begin{lstlisting}[style=grayverbatim,label={lst:sum_ranks_direct},caption={Sum of ranks using direct array data communication}]
from mpi4py import MPI
import numpy as np

# get comm, size, rank & host name
comm = MPI.COMM_WORLD
size = comm.Get_size()
rank = comm.Get_rank()
proc = MPI.Get_processor_name()


total = np.array(rank,dtype=np.int32)
current_value = np.array(rank,dtype=np.int32)
received_value = np.array(0,dtype=np.int32)
for _ in range(size - 1):
    comm.Sendrecv(
        current_value,
        dest=(rank + 1) % size,
        sendtag=0,
        recvbuf=received_value,
        source=(rank - 1 + size) % size,
        recvtag=0,
    )

    total += received_value
    current_value[...] = received_value

print(f"Sum is {total} on processor {proc}, rank {rank} out of {size} "
      f"processes")
\end{lstlisting}
This second implementation uses the same ring algorithm as the previous one, but it replaces the
pickle-based communication with direct buffer communication. In mpi4py, methods whose names start
with an upper-case letter, such as \texttt{Sendrecv}, operate directly on memory buffers. For this
reason, the communicated values are stored in NumPy arrays with an explicit datatype,
\texttt{np.int32}. This allows mpi4py to infer the corresponding MPI datatype and send the raw array
data without serializing a Python object.\\

The variables \texttt{total}, \texttt{current\_value}, and \texttt{received\_value} are zero-dimensional
NumPy arrays. The array \texttt{current\_value} is sent to the right neighbour, while
\texttt{received\_value} is used as the receive buffer for the value arriving from the left neighbour.
After each communication step, the received value is added to the local accumulator
\texttt{total}. The instruction
\texttt{current\_value[...] = received\_value} updates the content of the existing NumPy buffer
in-place. This is preferable to rebinding the variable name, because the MPI routine expects buffer-like
objects with well-defined memory storage.\\

As in the pickle-based implementation, the neighbour ranks are computed with modulo arithmetic:
\texttt{(rank + 1) \% size} is the destination rank and
\texttt{(rank - 1 + size) \% size} is the source rank. The addition of \texttt{size} before the modulo
operation avoids negative ranks when \texttt{rank = 0}. After \texttt{size - 1} communication steps,
each process has received all other ranks and has therefore reconstructed the global sum locally.

\subsection{Ghost cell exchange between neighboring processes [5 Points]}
Here we were asked to create a two-dimensional, periodic Cartesian topology and implement ghost cell exchange.\\
In listing \ref{lst:ghost_exchange_python} we can see the implementation of the ghost cell exchange between neighboring processes in Python using mpi4py.
\begin{lstlisting}[style=grayverbatim,label={lst:ghost_exchange_python},caption={Ghost cell exchange between neighboring processes in Python using mpi4py}]
from mpi4py import MPI
import numpy as np

# get comm, size, rank & host name
comm = MPI.COMM_WORLD
size = comm.Get_size()
rank = comm.Get_rank()
proc = MPI.Get_processor_name()

SUBDOMAIN_SIZE = 6
DOMAIN_SIZE = SUBDOMAIN_SIZE + 2

comm = MPI.COMM_WORLD
rank = comm.Get_rank()
size = comm.Get_size()

# Initialization
data = np.full((DOMAIN_SIZE, DOMAIN_SIZE), -1, dtype=np.int32)
data[1:-1, 1:-1] = rank

dims = [3, 4]
periods = [True, True]

cart = comm.Create_cart(dims=dims, periods=periods, reorder=False)

rank_south, rank_north = cart.Shift(1, 1)
rank_west, rank_east   = cart.Shift(0, 1)

# North/South exchange
cart.Sendrecv(
    sendbuf=data[DOMAIN_SIZE-2, 1:-1],
    dest=rank_north,
    sendtag=0,
    recvbuf=data[0, 1:-1],
    source=rank_south,
    recvtag=0
)

cart.Sendrecv(
    sendbuf=data[1, 1:-1],
    dest=rank_south,
    sendtag=1,
    recvbuf=data[DOMAIN_SIZE-1, 1:-1],
    source=rank_north,
    recvtag=1
)

# West/East exchange: columns are not contiguous, so use temporary arrays
recv_west = np.empty(SUBDOMAIN_SIZE, dtype=np.int32)
recv_east = np.empty(SUBDOMAIN_SIZE, dtype=np.int32)

send_east = np.ascontiguousarray(data[1:-1, DOMAIN_SIZE-2])
send_west = np.ascontiguousarray(data[1:-1, 1])

cart.Sendrecv(
    sendbuf=send_east,
    dest=rank_east,
    sendtag=2,
    recvbuf=recv_west,
    source=rank_west,
    recvtag=2
)
data[1:-1, 0] = recv_west

cart.Sendrecv(
    sendbuf=send_west,
    dest=rank_west,
    sendtag=3,
    recvbuf=recv_east,
    source=rank_east,
    recvtag=3
)
data[1:-1, DOMAIN_SIZE-1] = recv_east

\end{lstlisting}
Each MPI process owns a local subdomain of size
\texttt{SUBDOMAIN\_SIZE} by \texttt{SUBDOMAIN\_SIZE}. The full local array \texttt{data} has size
\texttt{DOMAIN\_SIZE} by \texttt{DOMAIN\_SIZE}, where
\texttt{DOMAIN\_SIZE = SUBDOMAIN\_SIZE + 2}. The additional two rows and columns are the ghost
layers. The interior entries \texttt{data[1:-1, 1:-1]} are initialized with the MPI rank of the process,
while the ghost cells are initialized to \texttt{-1}. After the exchange, the ghost cells should contain
the rank numbers of the neighbouring processes.\\

The Cartesian topology is created with \texttt{comm.Create\_cart}. In this implementation, the process
grid is fixed to \texttt{dims = [3, 4]}, meaning that the 12 MPI processes are arranged in a
two-dimensional grid with 3 processes in one direction and 4 processes in the other. The array
\texttt{periods = [True, True]} makes the topology periodic in both directions. Therefore, processes
on the boundary of the process grid still have neighbours: for example, the process at the right
boundary has as east neighbour the corresponding process at the left boundary.\\
The neighbours are obtained using \texttt{cart.Shift}. The call
\texttt{cart.Shift(1, 1)} returns the neighbours in the second Cartesian direction, which are used here
as the south and north neighbours. Similarly, \texttt{cart.Shift(0, 1)} returns the neighbours in the
first Cartesian direction, used here as the west and east neighbours. This avoids manually computing
neighbour ranks and makes the code independent of the rank ordering inside the Cartesian communicator.\\

The north/south exchange communicates rows. Since NumPy arrays are stored in row-major order, slices
such as \texttt{data[DOMAIN\_SIZE-2, 1:-1]} and \texttt{data[1, 1:-1]} are contiguous in memory.
Therefore, they can be passed directly to \texttt{Sendrecv}. The last interior row is sent to the north
neighbour and the first ghost row is filled with data received from the south neighbour. Conversely, the
first interior row is sent to the south neighbour and the last ghost row is filled with data received from
the north neighbour.\\
The west/east exchange communicates columns. In row-major storage, columns are not contiguous in
memory. For this reason, the code first creates contiguous temporary send buffers using
\texttt{np.ascontiguousarray}. The east interior column is copied into \texttt{send\_east}, and the west
interior column is copied into \texttt{send\_west}. The received columns are stored in the temporary
arrays \texttt{recv\_west} and \texttt{recv\_east}, and then copied into the corresponding ghost columns
of \texttt{data}. This avoids problems associated with sending non-contiguous NumPy views directly.

The use of \texttt{Sendrecv} again prevents deadlocks. All processes participate in the same pairwise
exchange pattern, and each call simultaneously sends one boundary buffer and receives the corresponding
ghost buffer. Different message tags are used for the two directions of each exchange. This makes the
matching of messages unambiguous and prevents a message from one exchange direction from being
incorrectly matched with another one.

\subsection{A self-scheduling example: Parallel Mandelbrot [30 Points]}
\subsubsection{Implementation}
Here we were asked to implement the manager-worker pattern to compute the Mandelbrot set in parallel. The manager process is responsible for distributing the work and collecting the results, while the worker processes perform the actual computation of the Mandelbrot set for assigned tasks.\\
The implementation of the manager-worker pattern for computing the Mandelbrot set is provided in the listing \ref{lst:mandelbrot_manager_worker}.
\begin{lstlisting}[style=grayverbatim,label={lst:mandelbrot_manager_worker},caption={Manager-worker pattern for computing the Mandelbrot set in parallel}]
# some parameters
MANAGER = 0       # rank of manager
TAG_TASK      = 1 # task       message tag
TAG_TASK_DONE = 2 # tasks done message tag
TAG_DONE      = 3 # done       message tag

def manager(comm, tasks):
    size = comm.Get_size()
    nworkers = size - 1

    next_task = 0
    active_workers = 0
    TasksDoneByWorker = {i: 0 for i in range(size)}

    # send initial tasks
    for worker in range(1, size):
        if next_task < len(tasks):
            comm.send((next_task, tasks[next_task]), dest=worker, tag=TAG_TASK)
            next_task += 1
            active_workers += 1
        else:
            comm.send(None, dest=worker, tag=TAG_DONE)

    # receive results and assign new tasks
    status = MPI.Status()

    while active_workers > 0:
        task_id, completed_task = comm.recv(
        source=MPI.ANY_SOURCE,
        tag=TAG_TASK_DONE,
        status=status
        )

        worker = status.Get_source()
        TasksDoneByWorker[worker] += 1

        # replace the completed task in the task list
        tasks[task_id] = completed_task

        if next_task < len(tasks):
            comm.send((next_task, tasks[next_task]), dest=worker, tag=TAG_TASK)
            next_task += 1
        else:
            comm.send(None, dest=worker, tag=TAG_DONE)
            active_workers -= 1

    return TasksDoneByWorker


def worker(comm):
    while True:
        status = MPI.Status()
        message = comm.recv(source=MANAGER, tag=MPI.ANY_TAG, status=status)

        if status.Get_tag() == TAG_DONE:
            break

        task_id, task = message
        task.do_work()

        comm.send((task_id, task), dest=MANAGER, tag=TAG_TASK_DONE)

def readcmdline(rank):
    """
    Read command line arguments

    Parameters
    ----------
    rank : int
        Rank of calling MPI process

    Returns
    -------
    nx : int
        number of gridpoints in x-direction
    ny : int
        number of gridpoints in y-direction
    ntasks : int
        number of tasks
    """
    # report usage
    if len(sys.argv) != 4:
        if rank == MANAGER:
            print("Usage: manager_worker nx ny ntasks")
            print("  nx     number of gridpoints in x-direction")
            print("  ny     number of gridpoints in y-direction")
            print("  ntasks number of tasks")
        sys.exit()

    # read nx, ny, ntasks
    nx = int(sys.argv[1])
    if nx < 1:
        sys.exit("nx must be a positive integer")
    ny = int(sys.argv[2])
    if ny < 1:
        sys.exit("ny must be a positive integer")
    ntasks = int(sys.argv[3])
    if ntasks < 1:
        sys.exit("ntasks must be a positive integer")

    return nx, ny, ntasks


if __name__ == "__main__":

    # get COMMON WORLD communicator, size & rank
    comm    = MPI.COMM_WORLD
    size    = comm.Get_size()
    my_rank = comm.Get_rank()

    # report on MPI environment
    if my_rank == MANAGER:
        print(f"MPI initialized with {size:5d} processes")

    # read command line arguments
    nx, ny, ntasks = readcmdline(my_rank)

    # start timer
    timespent = - time.perf_counter()

    if my_rank == MANAGER:
        x_min = -2.
        x_max = +1.
        y_min = -1.5
        y_max = +1.5

        M = mandelbrot(x_min, x_max, nx, y_min, y_max, ny, ntasks)
        tasks = M.get_tasks()

        if size == 1:
            for task in tasks:
                task.do_work()
            TasksDoneByWorker = {0: len(tasks)}
        else:
            TasksDoneByWorker = manager(comm, tasks)

        m = M.combine_tasks(tasks)
        plt.imshow(m.T, cmap="gray", extent=[x_min, x_max, y_min, y_max])
        plt.savefig("mandelbrot.pdf")

        timespent += time.perf_counter()

        print(f"Run took {timespent:f} seconds")
        for i in range(size):
            print(f"Process {i:5d} has done {TasksDoneByWorker.get(i, 0):10d} tasks")
        print("Done.")

    else:
        worker(comm)
\end{lstlisting}
This listing implements a dynamic manager-worker algorithm. The process with rank zero is assigned
the role of manager, while all other MPI processes are workers. The manager is responsible for creating
the Mandelbrot tasks, distributing them to the workers, collecting the completed tasks, and finally
assembling the global image. The workers do not communicate with each other; they only receive tasks
from the manager and send completed results back to it.\\

The constants \texttt{TAG\_TASK}, \texttt{TAG\_TASK\_DONE}, and \texttt{TAG\_DONE} define the message
types used in the program. Tags are important because the same pair of processes can exchange
different kinds of messages. A message with tag \texttt{TAG\_TASK} contains a new task to compute,
a message with tag \texttt{TAG\_TASK\_DONE} contains a completed task returned by a worker, and a
message with tag \texttt{TAG\_DONE} tells a worker that no more tasks are available and that it can
terminate.\\

Inside the \texttt{manager} function, the variable \texttt{next\_task} stores the index of the next
unassigned task. The variable \texttt{active\_workers} counts how many workers are currently working
on a task. At the beginning, the manager sends one task to each worker, as long as tasks are available.
If there are more workers than tasks, the extra workers immediately receive a \texttt{TAG\_DONE}
message. This initialization phase fills the available workers with work and starts the computation.\\
After the initial distribution, the manager enters a loop that continues while at least one worker is
active. The manager receives completed tasks using
\texttt{comm.recv(source=MPI.ANY\_SOURCE, tag=TAG\_TASK\_DONE, status=status)}. The use of
\texttt{MPI.ANY\_SOURCE} is essential for dynamic scheduling: the manager does not wait for a
particular worker, but accepts the result from whichever worker finishes first. This allows faster workers
or workers assigned easier Mandelbrot patches to immediately receive more work, improving load
balance.\\
The received message contains both the \texttt{task\_id} and the completed task object. The task
identifier is needed because tasks may return in a different order from the one in which they were sent.
The manager therefore uses \texttt{tasks[task\_id] = completed\_task} to put the result back into the
correct position in the task list. This guarantees that the final call to \texttt{combine\_tasks} can
reconstruct the Mandelbrot image correctly.\\

Once a worker returns a result, the manager checks whether more tasks are available. If
\texttt{next\_task < len(tasks)}, the same worker immediately receives a new task. Otherwise, the
worker receives a termination message with tag \texttt{TAG\_DONE}, and the number of active workers is
decreased. When all workers have received \texttt{TAG\_DONE}, \texttt{active\_workers} becomes zero and
the manager loop terminates.\\

The \texttt{worker} function is a simple infinite loop. Each worker waits for a message from the
manager using \texttt{comm.recv}. The tag of the received message is inspected through the
\texttt{MPI.Status} object. If the tag is \texttt{TAG\_DONE}, the worker exits the loop and terminates.
Otherwise, the message contains a Mandelbrot task. The worker calls \texttt{task.do\_work()}, which
computes the Mandelbrot patch locally, and then sends the completed task back to the manager with tag
\texttt{TAG\_TASK\_DONE}.\\

In the main part of the program, all MPI processes first obtain the communicator, the total number of
processes, and their rank. The manager prints the number of MPI processes and creates the global
Mandelbrot object. The call \texttt{M.get\_tasks()} decomposes the global image into independent
patches. If the program is run with only one MPI process, there are no workers. In this special case,
the manager computes all tasks sequentially by directly calling \texttt{task.do\_work()} for every task.
This makes the code valid also for \texttt{size = 1} and provides a useful serial reference.\\
For \texttt{size > 1}, the manager calls the \texttt{manager} function to perform the dynamic parallel
scheduling. After all tasks have been completed, \texttt{M.combine\_tasks(tasks)} assembles the full
Mandelbrot image from the computed patches.

The near-equal number of completed tasks does not necessarily mean that all workers performed exactly
